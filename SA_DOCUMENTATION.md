## Algorithm Overview

Simulated Annealing (SA) is a probabilistic metaheuristic inspired by the
annealing process in metallurgy — where a material is heated to a high
temperature and then slowly cooled to reach a low-energy (optimal) crystalline
structure.

In the context of railway scheduling, SA searches for the train ordering
(permutation) that minimizes total weighted delay across all platforms.

### Pseudocode

```
INPUT:  trains, constraints, cooling parameters
OUTPUT: best schedule found

current ← arrival_time_order(trains)
best    ← current
T       ← calibrate_temperature(current)

WHILE T > T_min AND iteration < max_iterations:
    neighbor ← perturb(current)            # swap / insert / adj_swap
    Δ       ← fitness(neighbor) - fitness(current)

    IF Δ < 0:
        current ← neighbor                 # always accept improvements
    ELSE:
        IF random() < exp(-Δ / T):
            current ← neighbor             # sometimes accept worse

    IF fitness(current) < fitness(best):
        best ← current                     # track global best

    T ← T × cooling_rate                   # cool down

RETURN best
```

## Why Simulated Annealing?

SA was chosen as the comparison algorithm because:

1. **Complementary paradigm** — SA is a single-trajectory metaheuristic,
   while GA is a population-based metaheuristic. Comparing them reveals
   fundamental trade-offs between exploration breadth (GA) and focused
   exploitation (SA).

2. **Theoretical foundations** — SA has provable convergence guarantees
   under ideal cooling schedules (Geman & Geman, 1984). This provides
   a theoretical baseline.

3. **Simplicity** — SA has fewer hyperparameters than GA (no crossover
   rate, population size, elitism ratio, tournament size). This makes
   it easier to tune and reason about.

4. **Memory efficiency** — SA maintains only 2 solutions in memory at
   any time (current + best), versus GA's entire population.

5. **Permutation friendliness** — Unlike GA, SA does not require a
   specialized crossover operator to maintain valid permutations.
   Simple swap/insert operators naturally preserve validity.

## Implementation Details

### Initial Solution

The initial schedule is generated by sorting trains in **arrival-time order**:

```python
initial_solution = np.argsort(arrivals)
```

This is a deterministic, non-random starting point that:
- Produces a naturally low-delay baseline
- Is the same ordering used by the FCFS baseline
- Gives SA a strong starting point to improve upon

### Fitness Function

The SA implementation uses the **exact same** `evaluate_schedule_numba()` function
as the Genetic Algorithm. This numba-compiled function:

1. Simulates the schedule execution in order
2. Tracks platform availability with headway constraints
3. Computes delay = max(0, actual_start − arrival_time) for each train
4. Returns the total **weighted delay** (delay × priority weight)

The fitness function is imported directly from `ga_scheduler.py` — it is not
duplicated or modified.

### Acceptance Criterion (Metropolis)

For each candidate neighbor:

```
Δ = fitness(neighbor) - fitness(current)

if Δ < 0:   accept (improvement)
else:        accept with probability P = exp(-Δ / T)
```

At high temperatures, P is close to 1 → almost all moves accepted (exploration).
At low temperatures, P approaches 0 → only improvements accepted (exploitation).

### Best Solution Tracking

Two solutions are maintained throughout:

| Variable | Purpose |
|---|---|
| `current_solution` | The working solution — may accept worse moves |
| `best_solution` | The global best — never overwritten with worse |

This ensures the global optimum found during the entire run is never lost,
even as the current solution explores worse regions of the search space.

## Neighbor Generation

Three perturbation operators are used, selected probabilistically each iteration:

### 1. Swap (40%)

Swap two random positions in the permutation.

```
Before: [A, B, C, D, E, F]
                ↑        ↑
After:  [A, B, F, D, E, C]
```

- **Magnitude**: Large — trains can be far apart
- **Purpose**: Exploration, escaping local minima
- **Validity**: Preserves permutation (no duplicates)

### 2. Insert (40%)

Remove a train from one position and insert it at another.

```
Before: [A, B, C, D, E, F]
              remove ↑
After:  [A, B, D, E, C, F]
                     insert ↑
```

- **Magnitude**: Medium — preserves most of the relative order
- **Purpose**: Repositioning individual trains without disrupting others
- **Validity**: Preserves permutation (remove + insert = same elements)

### 3. Adjacent Swap (20%)

Swap two adjacent trains.

```
Before: [A, B, C, D, E, F]
              ↑  ↑
After:  [A, B, D, C, E, F]
```

- **Magnitude**: Small — minimal disruption
- **Purpose**: Fine-tuning, local refinement
- **Validity**: Preserves permutation

### Why This Mix?

The 40/40/20 split provides:

- **Early search (high T)**: Swap and Insert operators dominate, enabling
  large exploratory jumps across the solution space.
- **Late search (low T)**: All three operators contribute, but the algorithm
  increasingly rejects large worsening moves, effectively making adjacent
  swaps the dominant accepted operator for fine-tuning.

## Temperature Cooling

### Exponential Cooling (Default)

```python
T_new = T_current × COOLING_RATE
```

With `COOLING_RATE = 0.995`:

| Iteration | Temperature (% of T0) |
|---|---|
| 0 | 100.0% |
| 100 | 60.7% |
| 500 | 8.2% |
| 1000 | 0.7% |
| 2000 | 0.005% |

The cooling schedule is **pluggable**. The `run_simulated_annealing()` function
accepts a `cooling_fn` parameter with signature:

```python
def cooling_fn(temperature: float, cooling_rate: float) -> float
```

Future strategies (linear, logarithmic, adaptive) can be added by simply
defining a new function with this signature.

## Adaptive Temperature Calibration

The initial temperature T0 is **not hardcoded**. Instead, it is computed
automatically using the method of Ben-Ameur (2004):

1. Generate 200 random neighbors of the initial solution
2. Evaluate fitness of each neighbor
3. Compute delta = neighbor_fitness − initial_fitness for each
4. Collect all **positive** deltas (uphill moves)
5. Compute average positive delta (avg_Δ)
6. Set T0 = −avg_Δ / ln(target_acceptance)

With `target_acceptance = 0.8`:

```
T0 = −avg_Δ / ln(0.8)
T0 ≈ avg_Δ / 0.2231
T0 ≈ 4.48 × avg_Δ
```

This ensures that at T0, approximately 80% of uphill moves are accepted,
regardless of:
- Problem scale (number of trains)
- Fitness magnitude (penalty weights)
- Constraint tightness (headway, maintenance windows)

The temperature automatically adapts to the problem.

## Complexity Analysis

### Time Complexity

| Component | Complexity | Notes |
|---|---|---|
| Initial solution | O(N log N) | Sorting by arrival time |
| Temperature calibration | O(S × N) | S samples × O(N) fitness each |
| Each SA iteration | O(N) | Neighbor generation + fitness evaluation |
| Total iterations | O(I) | I = max(25000, N × 500) |
| **Total per run** | **O(I × N)** | Dominated by the main loop |
| **Total with restarts** | **O(R × I × N)** | R restarts |

Where:
- N = number of trains
- S = calibration samples (200)
- I = max iterations (N × 500)
- R = number of restarts (10)

**Concrete examples:**

| Trains | Max Iterations | Total Fitness Evals | Approx. Time* |
|---|---|---|---|
| 50 | 25,000 | 252,000 | ~2s |
| 100 | 50,000 | 502,000 | ~5s |
| 500 | 250,000 | 2,502,000 | ~30s |
| 1000 | 500,000 | 5,002,000 | ~120s |

*Approximate, depends on hardware. Numba JIT compilation makes fitness
evaluation very fast (microseconds per call).

### Space Complexity

| Component | Space | Notes |
|---|---|---|
| Current solution | O(N) | One int32 array |
| Best solution | O(N) | One int32 array |
| Neighbor (temporary) | O(N) | Created each iteration, recycled |
| Convergence history | O(I / LOG_INTERVAL) | One tuple per interval |
| Numba data arrays | O(N) | Shared with GA |
| **Total** | **O(N)** | Constant factor ~5 arrays |

SA uses dramatically less memory than GA, which maintains a population
of `POP_SIZE` (500) solutions simultaneously.

## Comparison with Genetic Algorithm

### Structural Differences

| Aspect | Genetic Algorithm | Simulated Annealing |
|---|---|---|
| Paradigm | Population-based | Single-trajectory |
| Solutions in memory | 500 (POP_SIZE) | 2 (current + best) |
| Variation operator | Crossover + Mutation | Neighbor perturbation |
| Selection | Tournament (k=3) | Metropolis acceptance |
| Diversity mechanism | Population + Elitism | Temperature-controlled acceptance |
| Parallelism | Natural (population) | Restarts only |
| Crossover required | Yes (order crossover) | No |
| Convergence theory | Schema theorem (heuristic) | Provable (under ideal cooling) |

### Expected Performance Characteristics

| Metric | GA Expected | SA Expected | Rationale |
|---|---|---|
| Solution quality | **Better** | Good | GA's population diversity explores more |
| Runtime (small N) | Moderate | **Faster** | SA has lower per-iteration overhead |
| Runtime (large N) | Moderate | Varies | Depends on iteration budget |
| Memory usage | Higher | **Lower** | 500 solutions vs 2 solutions |
| Scalability | **Better** | Moderate | Population parallelism |
| Ease of tuning | More parameters | **Fewer parameters** | SA has ~4 params vs GA's ~6 |
| Reproducibility | Requires seeding | **Deterministic start** | Same initial solution always |

### Advantages of SA

1. **Memory efficiency** — O(N) vs O(POP_SIZE × N)
2. **Simplicity** — fewer hyperparameters, no crossover operator
3. **No validity concerns** — neighbor operators naturally preserve permutations
4. **Theoretical guarantees** — provable convergence under logarithmic cooling
5. **Adaptive temperature** — auto-calibrates to problem scale

### Disadvantages of SA

1. **Single trajectory** — explores one path through the solution space
2. **No recombination** — cannot combine good parts of two different solutions
3. **Harder to parallelize** — restarts are independent but don't share information
4. **Sensitive to cooling rate** — too fast → premature convergence; too slow → waste
5. **No population diversity** — relies entirely on temperature for exploration

## Parameter Tuning Guide

### Key Parameters

| Parameter | Default | Range | Effect |
|---|---|---|---|
| `COOLING_RATE` | 0.995 | 0.990–0.999 | Lower = faster cooling, risk of premature convergence |
| `MIN_TEMPERATURE` | 0.01 | 0.001–0.1 | Lower = more iterations in exploitation phase |
| `ITERATIONS_PER_TRAIN` | 500 | 200–2000 | Higher = more thorough search, longer runtime |
| `INITIAL_ACCEPTANCE_PROB` | 0.8 | 0.5–0.95 | Higher = more initial exploration |
| `SA_RUNS` | 10 | 3–20 | More runs = better chance of finding global optimum |
| `SWAP_PROBABILITY` | 0.40 | 0.2–0.6 | Higher = more exploration |
| `INSERT_PROBABILITY` | 0.40 | 0.2–0.6 | Higher = more structural changes |

### Tuning Strategy

1. **Start with defaults** — they are calibrated for the railway scheduling problem
2. **If solutions are poor** — increase `ITERATIONS_PER_TRAIN` or `SA_RUNS`
3. **If runtime is too long** — decrease `ITERATIONS_PER_TRAIN` or `SA_RUNS`
4. **If stuck in local minima** — increase `SWAP_PROBABILITY` or `INITIAL_ACCEPTANCE_PROB`
5. **If solutions are unstable** — decrease `COOLING_RATE` (slower cooling)

## Usage Instructions

### Running SA Standalone

```bash
python sa_scheduler.py
```

This runs the SA optimizer on the default 50-train scenario and produces:
- Console output with best score and schedule
- `sa_train_schedule.png` — Gantt chart of the optimized schedule

### Running the Benchmark

```bash
python benchmark.py
```

This runs FCFS, SA, and GA on the same scenario and produces:
- Comparison table with all metrics
- `fcfs_schedule.png`, `sa_schedule.png`, `ga_schedule.png` — Gantt charts
- `convergence_comparison.png` — SA convergence curve

### Running the Scalability Benchmark

```bash
python benchmark.py --scalability
```

Additionally tests 50, 100, 250, 500, and 1000 trains and produces:
- `scalability_comparison.png` — three-panel comparison plot

### Switching Between GA and SA

```python
from ga_scheduler import SchedulerService, build_combined_scenario
from sa_scheduler import SASchedulerService

snapshot = build_combined_scenario()

# Use GA
ga_service = SchedulerService({}, snapshot.maintenance_windows)
ga_result = ga_service.optimize(snapshot)

# Use SA
sa_service = SASchedulerService({}, snapshot.maintenance_windows)
sa_result, sa_history = sa_service.optimize(snapshot)

# Both return OptimizationResult — same fields, same format
print(ga_result.objective_score, sa_result.objective_score)
```
